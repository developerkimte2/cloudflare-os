## A3. 信頼度不足の次アクション提案を「AI の提案」として見せ、1 タップで採用 【小】

### 背景
`pipeline/ingest.ts` の「5. Next actions」で、`confidence < nextActionAutoConfidence (0.85)` の提案は `skipped` に入り、NEXT_ACTION 決定の `appliedJson: { nextActionIds, skipped }` に残るだけで画面に出ない。実測 27 件中 23 件がこれ。

### データ
- `skipped[]` の要素は抽出 JSON の `next_actions[]` そのもの (`action_type, title, purpose, due_at, due_confidence, priority, confidence`)。
- 採用・却下の記録: 同じ決定の `appliedJson` に `adopted: number[]`, `dismissed: number[]` (skipped の添字) を追記する。決定行の更新は `repo.updateDecision` (既存)。

### DTO (`sales-core/src/api/dto.ts`)
```ts
export interface NextActionSuggestion {
  decisionId: string;
  index: number;            // appliedJson.skipped の添字
  actionType: NextActionType;
  title: string;
  purpose: string;
  dueAt?: string;           // due_at が ISO なら通す (due_confidence は見ない。採用は人の判断)
  priority: Priority;
  confidence: number;
  createdAt: string;        // 決定の作成日時
}
```
- `CaptureResult` に `suggestions: NextActionSuggestion[]` (その取込の NEXT_ACTION 決定から)。
- `OpportunityDetail` に `suggestions: NextActionSuggestion[]` (その案件の NEXT_ACTION 決定すべて、新しい順、採用・却下済みは除く)。

### サービス (`service/sales-service.ts`)
- `private suggestionsFromDecisions(decisions: AIDecision[]): NextActionSuggestion[]` — `decisionType === "NEXT_ACTION"` の `appliedJson.skipped` を展開し、`adopted`/`dismissed` に含まれる添字を除く。
- `adoptSuggestion(actor, decisionId, index): NextAction` — 決定を取得 → 案件の可視性チェック (`canSee`) → `createNextAction` と同じ経路で作成 (`generatedBy: "AI"`, `sourceDecisionId: decisionId`, `recommendedAt: decision.createdAt`, `priority` は提案のもの、`dueAt` は ISO なら採用)。`appliedJson.adopted` に添字を追記。監査は `NEXT_ACTION_CREATED`。
- `dismissSuggestion(actor, decisionId, index): void` — `appliedJson.dismissed` に追記。監査 `SUGGESTION_DISMISSED` (labels に追加)。
- `getCapture` と `getOpportunity` に `suggestions` を載せる。

### RPC
`adoptSuggestion(decisionId, index): Promise<NextAction>`、`dismissSuggestion(decisionId, index): Promise<void>` を 3 か所に。`types.d.ts/txt` は触らない (エージェント向けには出さない)。

### UI
- `app/components/CaptureResultView.tsx`: 次アクションの下に「AI の提案（未確定）」節。行 = タイトル・目的・期限 (あれば)・優先度バッジ、右に「採用」「却下」。採用後は行が消え、通常の次アクション一覧に現れる。
- `app/pages/OpportunityDetailPage.tsx` の `NextActionsSection`: 未完了一覧の上に同じ節 (`data.suggestions`)。採用 → `api.adoptSuggestion` → reload。
- `app/labels.ts`: `AUDIT_ACTION_LABEL.SUGGESTION_DISMISSED = "AI提案を却下"`。

### テスト
- `pipeline.test.ts`: FakeLlm で `next_actions: [{... confidence: 0.7}]` → `capture()` の `suggestions` に 1 件、`nextActions` は 0 件。`adoptSuggestion` → `nextActions` 1 件、`suggestions` 0 件、`generatedBy === "AI"`, `sourceDecisionId` が決定 id。`dismissSuggestion` → 消える。他ユーザー (SALES、別案件) は `NotFoundError`。

コミット件名案: `Sales OS: surface low-confidence next-action suggestions for one-tap adoption`

## A2. 顧客の質問文を「メモを見せて選ばせる」形に。抽出された会社名の文らしさガード 【小〜中】

### 背景
実測: AI が「会社名は聞きそびれた」「山田太郎様」を会社名として返し、そのまま『「会社名は聞きそびれた」は既存顧客に見つかりません。新規顧客として登録しますか？』と質問された。

### 2-1. ガード (`rules/entity-resolution.ts`)
```ts
/** Strings the extractor sometimes returns *as* a company name that cannot be one. */
export function looksLikeCompanyName(name: string, personNames: string[]): boolean
```
偽 (= 会社名として扱わない) にする条件 (いずれか):
- 空、または 40 文字超
- `[。、！？!?]` を含む
- `/(不明|聞きそびれ|未定|わからない|分からない|未確認|なし|失念)/` を含む
- `/^(会社名|社名|顧客名|お客様|先方)/` で始まる
- `/(様|さん|殿)$/` で終わる
- `normalizeName(name)` が `personNames` のいずれかの `normalizeName` と一致 (人名を会社名にしている)

`resolveEntities` の先頭で `accounts` をこのガードでフィルタし、`persons[].company` も同様にフィルタ (該当なら `company` を null 扱い)。フィルタで空になれば従来の「本文に顧客名が含まれていない」経路に落ちる (A1 実装後は宛先確認へ)。
除外した名前は `AccountResolution.rejectedNames: string[]` に入れ、決定の `proposedJson` に残す (診断用)。

### 2-2. 質問文 (`pipeline/ingest.ts` の CUSTOMER_AMBIGUOUS 生成箇所)
`placeholder.displayName` を主語にしない。元メモの先頭 60 文字 (`source.rawText`、改行は空白に) を `excerpt` として:
- 候補あり: `メモ「{excerpt}」の顧客は「{mentionedCompanyName}」でよいですか？ 似た登録があります。`
- 候補なし・名前あり: `メモ「{excerpt}」の顧客「{mentionedCompanyName}」はまだ登録がありません。新しい顧客として登録しますか？`
- 名前なし (A1 まではここに来る): `メモ「{excerpt}」の顧客が分かりません。どの顧客の話ですか？`

選択肢 (`customerReviewOptions`) は今のまま (候補 / 新規 / どれでもない)。「新規顧客として登録」のラベルに名前が付くのも今のまま。

### 2-3. 任意 (時間があれば): プロンプトの明文化
`ai/skills.ts` 原則 8 の直後に 8-1 を追加し、`EXTRACTION_PROMPT_VERSION` を `extract.v2` に上げる:
> 8-1. 本文に会社名の手がかりが無いときは account_candidates を空配列にする。「会社名不明」「聞きそびれた」のような説明文や、人名を会社名として書かない。known accounts に載っている情報 (メールアドレス等) を、本文に書かれていないのに候補に書き写さない。

プロンプト版数を pin しているテストがあれば合わせる。

### テスト
- `rules-entity-resolution.test.ts`: `looksLikeCompanyName` の表 (上の各条件 1 つずつ + 正常な「ABC株式会社」「(株)グリーンフィールズ」「ABC Systems」は真)。`resolveEntities` に `accounts: [{name:"会社名は聞きそびれた"}]` → `method === "NONE"`, `mentionedCompanyName === undefined`, `rejectedNames` に入る。
- `pipeline.test.ts`: 会社名なし・人名ありの取込で、レビューの question がメモ抜粋を含み、抽出文字列を「顧客」として断定していない。

コミット件名案: `Sales OS: quote the memo in customer questions; reject non-company strings as company names`

## A1. メモの宛先を確定させる (案件からの取り込み / 「どの案件？」/ 顧客未特定案件の廃止) 【中】

### 背景
実測 31 件中 13 件が「(顧客未特定)」の新規案件 (案件名 = メモ本文) になった。原因: `CaptureOptions` に宛先が無く、案件画面からメモを投げられず、顧客名のないメモは必ず新規扱い。

### 1-1. 宛先つき取り込み
- **migration 0006** (`db/migrations.ts` 末尾):
  ```sql
  ALTER TABLE source_documents ADD COLUMN target_opportunity_id TEXT;
  ```
  `db/tables.ts` の `sourceDocuments` に `col("target_opportunity_id", "targetOpportunityId")`。`domain/types.ts` の `SourceDocument` に `targetOpportunityId?: string`。
- `CaptureOptions.opportunityId?: string` (dto)。`captureText` で受け取り、`source.targetOpportunityId` に保存 (再処理・非同期処理でも使えるように **必ず source に持たせる**)。`capture()`/`receive()` で `opportunityId` があれば可視性チェック (`canSee`)、無ければ `NotFoundError("案件")`。
- `pipeline/ingest.ts` `applyExtraction`: `source.targetOpportunityId` があれば **顧客判定をスキップ**: `opportunity = repo.getOpportunity(id)`, `account = repo.getAccount(opportunity.accountId)`, `opportunityBefore = {...opportunity}`、`decide("OPPORTUNITY_RESOLUTION", ..., { match: "PINNED", id }, ..., 1, "AUTO_APPLIED", "案件画面からの取り込み (宛先指定)")`。以降 (活動・約束・状態・次アクション) は既存の流れ。抽出の `entities`/`opportunity` は無視する (人物候補の新規作成は行う: 既存の `unmatchedPersons` の流れをこの経路でも通す。`resolveEntities` は呼んでよいが `account` は必ず宛先案件のもの)。
- `types.d.ts` / `types.txt`: `CaptureOptions` に `opportunityId?: string` (コメント: この案件のメモとして確定で紐付ける。顧客判定はしない)。

### 1-2. 顧客未特定メモ → 「どの案件？」(MEMO_TARGET)
- `domain/types.ts` `ReviewItemType` に `"MEMO_TARGET"` を追加 (テーブルの `type` に CHECK は無い)。`app/labels.ts` `REVIEW_TYPE_LABEL.MEMO_TARGET = "宛先の確認"`。
- `applyExtraction` で、顧客判定の結果が **`!resolution.account && !resolution.mentionedCompanyName && resolution.candidates.length === 0`** (会社名の手がかりが皆無) のとき、**案件・顧客プレースホルダ・活動・約束・次アクションを作らない**。代わりに:
  - review を 1 件: `type: "MEMO_TARGET"`, `relatedEntityType: "source_document"`, `relatedEntityId: source.id`, `assignedUserId: submitter.id`,
    `question: メモ「{excerpt}」はどの案件の話ですか？`,
    `options`: 提出者が見える進行中案件 (`listOpportunitiesVisibleTo(user, {lifecycleStates:["OPEN"], limit: 5})`、更新が新しい順) を `{ id: "opportunity:<id>", label: "<accountName> / <title>", value: { opportunityId } }` + `{ id: "memo", label: "案件に紐付けない（メモとして残す）", value: { memo: true } }`。
  - `decide("ENTITY_RESOLUTION", "source_document", source.id, ..., 0, "REVIEW_REQUIRED", "本文に顧客名が無いため宛先を確認")`。
  - source は `REVIEW_REQUIRED`。`source_applications` は作らない (作るなら `opportunityId` なしで `createdReviewIds` だけ)。
  - **「(顧客未特定)」プレースホルダの自動生成はこの経路では行わない** (`UNRESOLVED_ACCOUNT_NAME` は「会社名はあるが未登録」の経路にだけ残る)。
- **解決** (`service/sales-service.ts` `resolveReview`):
  - `resolveReview` を **async** にする (`Promise<ReviewDto>`)。既存テストの呼び出しに `await` を付ける (`smoke.test.ts`, `pipeline.test.ts` など。grep `resolveReview(`)。DO/管理 API は元から Promise。
  - `case "MEMO_TARGET"`:
    - `value.opportunityId` → 可視性チェック → `source.targetOpportunityId = value.opportunityId` で `updateSource` → review を RESOLVED にしてから `await processSource(ctx, source.id)` (1-1 の宛先つき経路で再処理。LLM をもう一度呼ぶ)。
    - `value.memo === true` → source を `PROCESSED` に更新 (活動は作らない。`rawText` が「最近の取込」に残るのが「メモとして残す」)。監査 `SOURCE_KEPT_AS_MEMO` (labels に追加)。
  - `settleSourceStatus` が MEMO_TARGET の source (application なし) でも落ちないことを確認。
- `revertCapture`: MEMO_TARGET のまま (application なし) の source を取り消したら review を dismissed にして source を `REVERTED` に。

### 1-3. UI
- `app/pages/OpportunityDetailPage.tsx`: 見出しの下 (顧客情報の前) に **簡易取り込み欄** (textarea 3 行 + 「この案件に取り込む」)。`CaptureBox` を再利用するなら `mode="pinned"` prop を足して質問モード・音声・一括を隠す。呼び出しは `api.capture(text, { opportunityId })`。結果は `CaptureResultView` をその場に表示し、`reload()`。

- 顧客ページからの取り込みは **P0 では入れない** (案件が複数あると宛先を選ばせる必要があるため)。

### テスト (`pipeline.test.ts`)

## A6. 取り込みを受付即応答にする (受付 → アラームで後処理) 【中・Opus 推奨】

### 背景
1 件 30 秒 (本番でも数秒〜十数秒)。画面はボタンが「取り込み中…」になるだけで、待てずに離れる・二度押しする。`receive()` (受付だけ) は DO と エージェント経路にあるが、管理画面は同期の `capture()` しか使っていない。

### 設計
- **sales-core** に `processPending(ctx, limit = 20): Promise<{ processed: string[]; remaining: number }>` を追加 (`pipeline/ingest.ts` か新規 `pipeline/queue.ts`): `processing_status = 'RECEIVED'` の source を `received_at` 昇順で取り、**1 件ずつ** `processSource` (それぞれ try/catch。`processSource` は失敗時に自ら FAILED にするので握りつぶさず、次へ進む)。`processSource` が開始時に `PROCESSING` にしていることを確認 (二重処理防止)。Repository に `listSourcesByStatus(status, limit)` を追加。
- **DO** (`sales-core-do.ts`):
  - `captureAsync(caller, text, options): Promise<{ sourceId: string; duplicate: boolean }>` = `receive()` + `await this.ctx.storage.setAlarm(Date.now())` (既にアラームがあればそのまま。`getAlarm()` で確認)。
  - `async alarm()`: `const r = await processPending(ctx)`; `if (r.remaining > 0) setAlarm(Date.now() + 1000)`。例外は log してアラームを再設定 (取りこぼし防止)。
  - 同期の `capture()` はエージェント用にそのまま残す。
  - 起動時 (`constructor`/`blockConcurrencyWhile` 内) に RECEIVED が残っていればアラームを設定 (再デプロイ後の取りこぼし防止)。
- **管理 API**: `captureAsync(text, options)` を 3 か所に。`getCapture` は既存。
- **UI** (`app/components/CaptureBox.tsx`, `BatchCaptureView.tsx`, `pages/TodayPage.tsx`):
  - 送信 → `captureAsync` → 即座に入力欄を空にし、「最近の取込」の先頭に **仮カード** (`受け付けました。整理中…`、バッジ「受付済み」) を出す。
  - `getCapture(sourceId)` を 3 秒ごとにポーリング。`processingStatus` が `RECEIVED`/`PROCESSING` 以外になったら `CaptureResultView` を表示し、`refresh()` (今日の再読込)。上限 5 分でポーリングをやめ「時間がかかっています。しばらくして「最近の取込」を確認してください」。
  - 質問モード (`askQuestion`) は同期のまま (検索は待ってよい)。
  - 一括取込は 1 行ずつ `captureAsync` し、各行を同様にポーリング。
- **注意**: 1 テナント 1 DO で逐次処理 → 20 人が同時に投げると最後尾は数分待つ。それでも画面は即応答なので体感は改善する。並列化はしない (LLM 側のレート・DO の CPU 制限を先に確認)。

### テスト
- sales-core: `processPending` — RECEIVED 3 件 (うち 1 件は LLM 失敗) → 2 件 PROCESSED/REVIEW_REQUIRED、1 件 FAILED、`remaining 0`。PROCESSING 中の件は拾わない。

- app テストは不要 (ポーリングは実機確認)。

コミット件名案: `Sales OS: accept a memo instantly and process it from a Durable Object alarm`

### 実装
- `db/repository.ts` に集計クエリ (SQL の GROUP BY。JS で全件を舐めない): 担当者別 OPEN 件数と金額合計、期限超過アクション (assigned_user_id)、停滞 (`COALESCE(last_meaningful_activity_at, updated_at) < ?`)、OPEN review (assigned_user_id)、取込 (submitted_by_user_id、received_at ≥ now-7d と max)。
- `getManagerSummary` (MANAGER/ADMIN のみ、既存) で組み立て。ユーザーは `active` を問わず全員 (無効は末尾)。
- UI (`app/pages/ManagerPage.tsx`):
  - 先頭に **KPI タイル 1 行** (7〜8 個、`flex-wrap`): 進行中 / 見込金額 / 今月受注 / 今月失注 / 停滞 / 高リスク / 期限超過 / 未確定顧客 / 確認待ち。金額は `toLocaleString("ja-JP")`。
  - 次に **担当者別の表**: 担当 / 進行中 / 見込額 / 期限超過 / 停滞 / 確認待ち / 最終記録 / 直近7日の記録。期限超過の多い順。期限超過・停滞が 0 でないセルは `text-kumo-danger`。最終記録が 3 日以上前は薄字で「N日前」。
  - 既存の段階別タイル・停滞・高リスク・契約手続き中・メンバー名簿は残す (下に移す)。
  - (任意) 担当者名クリック → 案件一覧を担当者で絞る。`Route` に `{ kind: "opportunities"; ownerUserId?: string }` を足し、`OpportunitiesPage` に `initialOwnerUserId` prop。
